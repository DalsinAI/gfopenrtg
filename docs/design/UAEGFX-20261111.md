# GFOpenRTG on UAE-family emulators (uaegfx)

Team 6, 11 November 2026: the design (sections 1 to 8). Team 5, the same
day: the backend as built (section 9) and the Picasso II plan (section 10).

Goal: GFOS gets RTG on Amiberry, WinUAE and FS-UAE. Tonight GFOS booted on
Amiberry 8.5 (Dale's PiMiga) to GFOpenUp Setup but did not use RTG.
GFOpenRTG today drives ACRTG only. Those emulators offer the `uaegfx`
Zorro II/III board.

This is a clean-room design for an open `uaegfx` backend in GFOpenRTG.
The open references are AROS's p96gfx/uaegfx path
(`arch/m68k-amiga/hidd/p96gfx/` and `arch/m68k-amiga/romboot/romboot.c`)
and the UAE-family board and trap contract in WinUAE (`expansion.cpp`,
`include/picasso96.h`), which Amiberry and FS-UAE share. The commercial
Picasso96 `uaegfx.card` is not a reference and must not be read.

A Team 5 agent is first checking whether the PiMiga GFOS Amiberry config
simply lacks the RTG board. Their result had not arrived when this note
was written. Adding the board, if it is missing, is necessary. It is not
enough on its own: GFOpenRTG still will not drive `uaegfx`. Keep this
design ready. Do not merge a driver until that check is in, and do not
ship a driver if the only problem was a missing board *and* some other
already-installed RTG stack would then have worked. For a stock GFOS
image that runs GFOpenRTG and not Picasso96, a backend is still needed
once the board is present.

## 1. Why tonight's boot could not have used RTG

`gfopenrtg.library` finds boards only by AmiCradle's manufacturer
(`0xDA15`, and the old id `2011`) and ACRTG product numbers 9, 15 and 16
(`library/openrtg_lib.c`, `find_boards`).

The ROM monitor (`library/openrtg_monitor_rom.c`) steps aside, keeping
nothing, when Picasso96's `rtg.library` is in memory **or no ACRTG board
is fitted**. On a UAE-family emulator there is no ACRTG board, so the
monitor never switches GFOpenRTG on.

`DESIGN.md` already says GFOpenRTG should load Picasso96 `.card` / `.chip`
drivers through BoardInfo, and it names UAE's `uaegfx.card`. The running
library does not do that yet. Screens are programmed through ACRTG
registers at the end of the board window (`library/screens.c`). Those
registers do not exist on `uaegfx`. VRAM on `uaegfx` is a plain memory
window; display control goes through the emulator's trap / `uaelib`
contract, not ACRTG MMIO.

So even with the `uaegfx` board in the Amiberry config, current GFOS
still boots on the chipset, which matches "Setup came up, but not on
RTG".

The old AmiCradle manufacturer `2011` is also UAE's usual manufacturer.
That is not a clash: ACRTG products are 9, 15 and 16; `uaegfx` is product
96. `FindConfigDev` must keep those product lists separate.

## 2. The board (config side)

WinUAE's `expamem_init_gfxcard` (the same contract Amiberry 8.5 and
FS-UAE use) autoconfigs a fake RTG board:

- Manufacturer `2011` (`hackers_id`), or `514` (Commodore) when the
  emulator is set to hide UAE ids (`uae_hide`).
- Product **96**.
- Zorro III or Zorro II, with a VRAM window at `cd_BoardAddr`. A Z3
  window is at least 16 MiB in the autoconfig size even if less VRAM is
  given; usable video RAM is the configured amount.
- Serial byte 3 is `1`. There is no diagnostic ROM vector on this board
  itself.

For the PiMiga GFOS Amiberry 8.5 config, the board has to be enabled, for
example as UAEGFX Zorro III, with a sensible VRAM size (16 MiB or more
on Z3; Z2 tops out at 8 MiB). The exact key names vary by wrapper
(`gfxcard_type` / `graphics_card=uaegfx` / `uaegfx-z3`, plus a memory
size). Team 5's check should say whether that board is in the config.
A 32-bit address space (68020+ / A1200) is required for Z3.

## 3. How the emulator is told to show a screen

`uaegfx` is not a Cirrus-style register file. The emulator shows RTG
when the guest calls into the UAE boot ROM's P96 vector (`p96romvector`).

The open way to get that vector, from AROS:

1. Call `uaelib` once early, before any injected `uaegfx.card` is
   `InitResident`'d. AROS does this from a COLDSTART module at priority
   -9, because the emulator's built-in card disables the direct RTG
   calls if `uaelib` has never been used. The safe probe is function
   **35** of `uaelib_demux` ("return whether RTG is enabled").
2. `OpenResource("uae.resource")`, then LVO -6 with the name
   `"uaelib_demux"`. That returns the vector.
3. If there is no `uae.resource`, try the old fixed address
   `$00F0FF60`. Accept it only when `(long & $FF00FFFF) == $A0004E75`.

Then, still from AROS's p96gfx card stubs, the first calls (function
number pushed, then JSR to the vector) are:

| Id | Call | What GFOpenRTG needs it for |
|---:|---|---|
| 16 | FindCard(BoardInfo in A0) | Claim the `uaegfx` board, fill memory base and size |
| 29 | InitCard(BoardInfo in A0 and A2) | Install the emulator's BoardInfo hooks |
| 18 | SetSwitch | Chipset or RTG in the host window |
| 21 | SetGC | Mode (width, height, format) |
| 22 | SetPanning | Visible origin and the start of the picture in VRAM |
| 26 | SetDisplay | Picture on or off |
| 19 | SetColorArray | 8-bit palette |
| 20 | SetDAC | Format of the DAC |

Blit and sprite calls (17, 23, 27, 28, 30, 31, 36–39, and the
BoardInfo sprite hooks) can wait. Phase 1 can draw with the existing
GFOpenRTG CPU path straight into VRAM, which the emulator already maps.

The BoardInfo layout and RGB format names (`RGBFB_CLUT`, `RGBFB_R5G6B5`,
`RGBFB_A8R8G8B8`, and the PC-swapped variants) are in the open WinUAE
header `include/picasso96.h` and in AROS `p96gfx_rtg.h`. GFOpenRTG
already uses CLUT, R5G6B5 and A8R8G8B8 on ACRTG. The backend must ask
`FindCard`/`InitCard` which formats this emulator actually displays, and
map to those. UAE often prefers a host-order 32-bit format (BGRA or
similar) in the window; do not assume ACRTG's A8R8G8B8 is shown as-is.

Call convention: push the function id, JSR to the vector, pop the id.
Arguments go in the usual Picasso96 registers (BoardInfo in A0, and so
on). Reimplement this in our own MIT sources. Do not copy AROS code
(APL) into this tree.

WinUAE can also inject a built-in `uaegfx.card`. On a GFOS image that
has no Picasso96, that card is not useful to us, and initialising it
first can shut the direct `uaelib` path. GFOpenRTG should take the AROS
route: probe `uaelib` first, then FindCard/InitCard ourselves, and not
rely on Picasso96 or on the injected card.

## 4. What changes in GFOpenRTG

A backend, not a new RTG system. One library, one display database, the
same screens and CPU (and later GFOpenGPU) drawing. Only the "find the
board / show this bitmap / palette / pointer / switch" edge is
different.

1. **Discovery.** `find_boards` also looks for manufacturer 2011 or 514,
   product 96. Record the board as type `uaegfx`, with VRAM at
   `cd_BoardAddr` and size from the ConfigDev (the usable amount, not
   necessarily the Z3 slot size). Do not treat ACRTG products 9, 15 or
   16 as `uaegfx`, even when the manufacturer is the old `2011`.
2. **Monitor start.** `gfopenrtg.monitor` and `C:GFOpenRTG ACTIVATE`
   stay running when an ACRTG board is absent but a `uaegfx` board is
   present (and `rtg.library` is not already in memory). Still step
   aside for Picasso96.
3. **Early `uaelib` probe.** A small COLDSTART module, or the same
   monitor module at a priority above any injected card, calls function
   35 once so the direct path stays alive.
4. **Show a screen.** For a `uaegfx` monitor, `screens.c` does not write
   ACRTG registers. It allocates the bitmap in the VRAM window, then
   calls SetGC, SetPanning, SetColorArray/SetDAC, SetDisplay and
   SetSwitch. Caps (largest size, formats, VRAM bytes) come from
   FindCard/InitCard, not from ACRTG `LIMIT` / `WANT_*`. There is no
   native-size host window protocol on `uaegfx`; offer the Standard and
   All mode lists as we do now, clipped to the board's max and VRAM.
5. **Pointer.** First phase can be a software pointer in the bitmap, or
   the BoardInfo sprite hooks if InitCard says the board has a hardware
   sprite. Do not program ACRTG sprite registers.
6. **Files.** Prefer a backend inside `gfopenrtg.library`
   (`library/uaegfx/` and a thin hook in `openrtg_lib.c` /
   `openrtg_monitor_rom.c` / `screens.c`) plus `DEVS:Monitors/UAEGFX`
   or the existing `GFOpenRTG` monitor with two board types. A later
   Picasso96-compatible `uaegfx.card` / `uaegfx.chip` pair, as
   `DESIGN.md` section 3 describes, can wait; GFOS does not need it to
   get a desktop.
7. **Several monitors.** First slice is one `uaegfx` board. A second
   UAE RTG board, if the emulator offers one, can follow the same
   FindCard loop.

On AmiCradle, behaviour must not change: ACRTG is still found first,
the monitor still starts from ACRTG, and `uaegfx` code is idle.

## 5. What this is not

- Not Picasso96, and not the commercial `uaegfx.card`.
- Not ACRTG-on-UAE. Do not pretend the UAE window speaks ACRTG
  registers.
- Not 3D on UAE in the first slice. There is no ACRTG.gpu / virgl ring
  here. Workbench, Setup, ScreenMode and 2D drawing are the goal.
  GFOpenGPU's CPU path can still draw into the bitmap later. Warp3D and
  MiniGL on this backend are a later task.
- Not a lab or PiMiga claim. This note is from the tree and from open
  references. No Amiberry, WinUAE or FS-UAE run is claimed.

## 9. As built (Team 5, 11 November 2026)

Team 5 built the backend on top of this design. Sections 1, 2, 4 and 5 hold
as written. One decision changed (the route to the board, 9.2) and one was
narrowed (where the backend hooks in, 9.3).

### 9.1 The config was not the problem

`amiberry --config GFOS.uae --dump-config` on Amiberry 8.5 (Pi and x86):
`gfxcard_type=ZorroIII`, `gfxcard_size=16`, `cpu_24bit_addressing=false`,
68040, `rtg_nocustom=true`, the same RTG keys as `TIS-MIG.uae`, which shows
RTG with Picasso96. Amiberry's log lists the board: `Card 06: 'UAE RTG'`,
MID 2011 PID 96, Z3 at `$50000000`, 16 MiB. GFOS stayed on the chipset only
because GFOpenRTG did not drive that board.

### 9.2 The route: the emulator's own uaegfx.card, not the uaelib vector

Section 3 chose AROS's route: the `uaelib` vector, function ids 16 to 40,
with an early probe (id 35) so the emulator does not install its own card.
Reading Amiberry 8.5's `osdep/picasso96.cpp` (for the interface only) shows
why that is fragile:

- Whenever the UAE boot ROM is in use (any directory drive or hardfile, as
  GFOS has), the emulator makes a library named `uaegfx.card` (version 3.5)
  as it mounts its drives, before DOS boots. Its log says
  `uaegfx.card 3.5 init`.
- Once that library exists, `uaelib` ids 16 to 40 are ignored ("obsolete
  Picasso96 uaelib hook called, call ignored"). The probe would have to win
  a race against the emulator's own mount, and it cannot from a disk.

So the backend uses that library, which is the emulator's code (GPL, in the
emulator), not Picasso96's: `FindCard` (-30) and `InitCard` (-36) with a
BoardInfo of our own; `InitCard` fills in the board's functions; GFOpenRTG
calls `SetGC`, `SetDAC`, `SetPanning`, `SetDisplay`, `SetSwitch`,
`SetColorArray` and, when the emulator offers a hardware sprite, `SetSprite`,
`SetSpriteImage`, `SetSpriteColor` and `SetSpritePosition`, through the
BoardInfo. That is the card-driver interface Picasso96 published, the same
one section 3 names, reached through the emulator's card instead of the
emulator's trap vector. The `uaelib` route is not built; it is only needed
on an emulator that makes no `uaegfx.card`, and none of the three does
while it has drives of its own.

The library uses only a `uaegfx.card` already in memory (never one from a
disk), and only when `rtg.library` is not running: Picasso96 has the board
then, and a second `FindCard` would take the card's BoardInfo from it.

### 9.3 Where it hooks in

`screens.c` and `openrtg_lib.c` already send everything a board does
through two functions, `reg()` and `rreg()` (ACRTG's register page). For
the uaegfx monitor those two call `library/uaegfx.c` instead of touching
memory: a mode, where the picture starts, the display, the switch, a pen
and the pointer become the board's calls (section 4, item 4); every read
answers 0, so nothing past ACRTG v0 (the ring, the card part, the watch,
the Native size) is switched on. Nothing reaches the emulator as
registers. This keeps the change to `screens.c` to a few lines and leaves
ACRTG's path byte for byte as it was.

- `find_boards` tries the uaegfx board only when no ACRTG board was
  found; on AmiCradle it is never tried. It is monitor 1. Its "board" is a
  ConfigDev of the library's own whose address and size are the video RAM
  `FindCard` reports (16 MiB on GFOS's config), so `ORTG_BoardAddress` and
  the mode table's VRAM sums are right. Largest picture 3840 x 2160; video
  RAM decides the rest (16 MiB: up to 1920 x 1200 in 32-bit).
- Formats: CLUT, R5G6B5 and A8R8G8B8, big-endian, as GFOpenRTG draws them.
  Amiberry converts any Picasso96 format for its window; its `rtg_modes`
  mask only limits what it advertises to Picasso96.
- The pointer: the chipset's sprite picture (16 pixels wide, two planes),
  the format `SetSpriteImage` takes. Only when the emulator's RTG hardware
  sprite is on (`gfxcard_hardware_sprite=true` in Amiberry). Without it
  there is no pointer on the RTG screen yet: a software pointer is a later
  step.
- **When.** Amiberry makes `uaegfx.card` as it mounts its drives, after the
  ROM's COLDSTART modules. So `gfopenrtg.monitor` in a GFOpenKick ROM
  (priority -38) finds no board on UAE and steps aside, unchanged. The disk
  monitor driver (`DEVS:Monitors/GFOpenRTG` 0.9) switches GFOpenRTG on. If
  the library was made before the card existed (from a ROM), it looks for
  boards again on the next `ORTG_MonitorCount`.
- **Which library.** A GFOpenKick ROM made before 0.26 holds a
  `gfopenrtg.library` that knows only ACRTG, and `OpenLibrary` of the name
  alone would make that one. Monitor driver 0.9 opens
  `LIBS:gfopenrtg.library` by path when the library is not in memory yet
  and the ROM's RomTag says a revision below 26. A ROM rebuilt with 0.26
  needs no disk copy.

### 9.4 What GFOS needs on a UAE-family emulator

1. `LIBS:gfopenrtg.library` 0.26 and `DEVS:Monitors/GFOpenRTG` 0.9.
2. The monitor driver run before IPrefs. GFOS's `S:Startup-Sequence` runs
   no monitors (on AmiCradle the ROM does it), so it gets
   `If EXISTS DEVS:Monitors/GFOpenRTG / DEVS:Monitors/GFOpenRTG >NIL: /
   EndIf` before `IPrefs`.
3. `Mount >NIL: DEVS:DOSDrivers/~(#?.info)`: on Amiberry `DH1:` is already
   mounted by the emulator, Mount's error opened the boot shell's window on
   the chipset Workbench, and with a window open IPrefs could not reopen
   Workbench on the RTG mode.
4. `ENVARC:Sys/screenmode.prefs` naming a GFOpenRTG mode: `$610A1200`,
   1920 x 1080 32-bit (on the PiMiga's 4K panel exactly 2x).
5. In the emulator: an RTG board (uaegfx, Z3, 16 MiB or more for
   1920 x 1080 32-bit; 32-bit addressing) and, for a pointer, the RTG
   hardware sprite on.

Nothing else: no Picasso96, no `uaegfx.card` file, no `Devs:Monitors/uaegfx`
(that file only tells Picasso96's rtg.library which card to load).

### 9.5 Tested

- Amiberry 8.5.0 x86_64 AppImage on daletop, GFOS's ROM pair and drives
  copied from the PiMiga, under a private Xvfb: the emulator logs
  `SetSwitch() - Picasso96 1920x1080x32` and the screenshot is OpenBench at
  1920 x 1080 on the RTG board; `ScreenTest` opened and closed an 800 x 600
  8-bit screen on it. `C:GFOpenRTG MODES` lists 45 modes, 320 x 200 to
  1920 x 1200, in 8, 16 and 32-bit. (Amiberry's x86 JIT stops this ROM on
  a blue screen before DOS with or without this change, so those runs were
  without JIT; the Pi's ARM64 JIT boots it.)
- The PiMiga (Pi 5, Amiberry 8.5.0): see the PR.
- Not yet tried: WinUAE, FS-UAE, Zorro II uaegfx, 8 and 16-bit Workbench,
  a second RTG board.

`C:GFOpenRTG` still prints "ACRTG at" for every board; cosmetic, for a
later change.

## 10. Picasso II plan (not built)

Dale, 11 November 2026: "we did have this lined up: UAEGFX and Picasso II".
The Picasso II is a real Zorro II card (Village Tronic), and the next
GFOpenRTG board after uaegfx.

### 10.1 The card

- Two Zorro II boards: manufacturer 2167 (Village Tronic), product 11 (the
  memory, 2 MiB of video RAM; 1 MiB on early cards) and product 12 (the
  registers: the Cirrus Logic chip's VGA I/O space, 64 KiB).
- The chip: Cirrus Logic CL-GD5426 on the Picasso II, CL-GD5428 on the
  Picasso II+. Both are VGA-compatible GD542x parts: sequencer, CRTC,
  graphics controller, attribute controller, the DAC (with the hidden DAC
  register for 15/16/24-bit) and the GD542x extensions (extended sequencer
  for the clock synthesiser, the CRTC's extended display start and offset
  bits, the BitBLT engine on the 5426 and 5428, a 32 x 32 or 64 x 64
  hardware cursor).
- Video RAM is a Zorro II window, segmented: the CPU sees 2 MiB through a
  bank/segment scheme (the 5426's GR9/GRA offset registers). No linear
  video RAM in the 68k's address space as on uaegfx.
- A monitor switch on the card (the chipset's picture or the card's).

### 10.2 What GFOpenRTG needs

A second backend at the same edge as uaegfx (`reg()`/`rreg()` and
`find_boards`), but this time the library programs the chip itself:

1. **Find** both boards (2167/11 and 2167/12) and pair them.
2. **Modes.** Program the GD542x for a mode: the VCLK synthesiser (numerator
   and denominator for the pixel clock), CRTC timings from a small table of
   VESA timings (640 x 480 to 1280 x 1024; 2 MiB limits 1024 x 768 to 16-bit
   and 800 x 600 to 24-bit), the extended sequencer for 8, 15/16 and 24-bit
   pixels, the hidden DAC register, and the display start and offset with
   the GD542x's extension bits. GFOpenRTG's 32-bit format becomes 24-bit
   packed or stays CLUT/16-bit on this card: the mode table's `formats`
   must say which (`caps.formats`), and `pixels.c` must learn a 24-bit
   packed bitmap, or the card offers 8 and 16-bit only to start with
   (simplest: 8 and 16-bit first).
3. **Video RAM access.** The CPU drawing path assumes linear video RAM.
   With the GD5426's 64 KiB banking, either keep screens in Fast RAM and
   copy changed rows into the card through the bank window (simple,
   correct, slow on a real Amiga), or bank per access (fast but touches
   every drawing path). Plan: Fast RAM shadow plus a dirty-rows copy, as
   `ORTG_WrittenSpans` already models, then the BitBLT engine for fills and
   copies later.
4. **Palette, switch, pointer:** the VGA DAC (index and data ports), the
   card's monitor switch, the GD542x hardware cursor.
5. **Endianness:** the card's 16-bit pixels are little-endian (PC); the
   16-bit format is R5G6B5PC, so `pixconv.h` needs that byte order or the
   card's byte-swap aperture if the 5428 offers it.

That is a real driver (a few thousand lines), unlike uaegfx's few hundred:
no host does the work.

### 10.3 Can it be tested on Amiberry 8.5?

Yes. Amiberry 8.5 emulates both boards (`gfxboard.cpp`, from WinUAE):
"Picasso II [Zorro II]" with a GD5426 and "Picasso II+ [Zorro II]" with a
GD5428, 2 MiB, with the switcher, through its built-in Cirrus emulation.
Config: `gfxcard_type=PicassoII+` (or `PicassoII`), `gfxcard_size=2`.
WinUAE has the same boards. A real Picasso II for the last check would be
Dale's to name.

### 10.4 Order

1. A host-tested GD542x mode calculator (clock and CRTC values for each
   listed size) and the board finder, with Amiberry's PicassoII+ board.
2. 8-bit Workbench from a Fast RAM shadow, the DAC, the switch.
3. 16-bit, the hardware cursor, then the BitBLT engine.

Clean room as for uaegfx: the Cirrus GD542x data books and VGA references
for the chip; emulator sources only to learn what the emulator expects;
no Picasso96 `PicassoII.card` or `CirrusGD542x.chip`.
